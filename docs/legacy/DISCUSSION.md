# FluxMind 项目现状总结与讨论

**生成时间**: 2026-06-21  
**目的**: 文档整理完成后，基于"轻量多用户（几个到十几个）"需求，讨论下一步方向

---

## 一、当前状态诊断

### ✅ 已完成的基础能力

1. **RAG 核心功能**
   - 30 篇论文语料库
   - FAISS 向量检索 + BM25 混合检索
   - 引用验证和溯源
   - 支持中英文界面

2. **基础设施**
   - Streamlit UI（单用户友好）
   - FastAPI 后端（支持 API 调用）
   - 已部署在 Trace-Twin（https://smy.hyper-dusty.cloud）
   - 本地作业队列和持久化

3. **安全和质量**
   - 641 个测试（89% 覆盖率）
   - 大量的 no-secret 安全投影
   - 完善的文档体系（已整理）

### 🔴 问题诊断

1. **功能停滞**
   - 最近 63 个提交几乎全是"sanitize/redact"安全清理
   - 真实功能（图像生成、代码沙箱）仍是 mock
   - 语料库停留在 30 篇

2. **定位混乱**
   - 按照"企业级 SaaS"标准建设
   - 实际需求是"轻量多用户（几个到十几个）"
   - 过度工程导致开发速度极慢

3. **优先级错位**
   - 90% 时间在完善安全边界
   - 10% 时间在真正的用户价值

## 二、针对"轻量多用户"的重新定位

### 场景定义

**用户规模**: 3-15 人（实验室/课题组内部）  
**使用方式**: 共享部署，简单权限控制  
**核心需求**: 
- 每个人能看到自己的查询历史
- 基本的访问控制（避免误操作）
- 真实的图像生成和代码执行

### 与"企业 SaaS"的区别

| 维度 | 企业 SaaS | 轻量多用户 | 当前实现 |
|------|-----------|-----------|---------|
| 用户数 | 100-10000+ | 3-15 | 按 10000+ 设计 ✗ |
| 认证 | OAuth/SSO | 简单密码/Token | 过度 hash 存储 ✗ |
| 权限 | RBAC + 精细控制 | 简单角色（admin/user） | 复杂 RBAC ✗ |
| 隔离 | 严格租户隔离 | 基本区分即可 | 过度投影 ✗ |
| 计费 | 精确到用户 | 统一配额 | 复杂计费归因 ✗ |
| 安全 | 多层防御 | 基础防护 | 过度安全投影 ✗ |

**结论**: 当前实现按"企业 SaaS"标准，但实际需求只是"轻量多用户"

---

## 三、需要保留的多用户功能

### ✅ 应该保留

1. **简单用户管理**
   - 用户名/密码或 API Token
   - 区分 admin/user 角色
   - 每个人有独立的查询历史

2. **基础访问控制**
   - 防止普通用户删除数据
   - 防止误操作影响他人
   - 基本的请求限流

3. **使用统计**
   - 谁查询了什么
   - 资源使用情况
   - 简单的 quota 提醒

### 🗑️ 可以简化/删除

1. **过度的安全投影**
   - 内部用户不需要防 XSS/注入
   - 不需要隐藏所有 request ID
   - 不需要复杂的 no-secret 层

2. **复杂的计费归因**
   - 不需要精确到每个请求的成本
   - 统一配额管理即可

3. **企业级 RBAC**
   - 不需要 viewer/member/admin/owner 四层
   - admin/user 两层足够

4. **分享链接系统**
   - 内部使用不需要公开分享
   - 直接给用户账号即可

## 四、提议的调整方向

### 方案 A：渐进式简化（推荐）

**保留现有架构，但简化实现**

#### 第一阶段：激活真实功能（1 周）
1. 接入 OpenAI 图像生成（替换 SVG mock）
2. 配置真实 Docker 沙箱（替换 subprocess）
3. 简化 product_registry 到"仅用户名+角色"
4. 删除 50% 的安全投影测试

#### 第二阶段：扩充内容（2 周）
1. 添加 20 篇新论文（目标 50 篇）
2. 优化检索质量
3. 写 3-5 个实际使用案例

#### 第三阶段：用户体验（1 周）
1. 添加简单的登录界面
2. 查询历史按用户隔离
3. 基础的 admin 面板

**优势**: 风险低，渐进式改进  
**劣势**: 仍保留一些冗余代码

---

### 方案 B：重构简化（激进）

**大幅删减，重新聚焦**

#### 要删除的
- `share_links.py` 及相关（内部不需要）
- 90% 的 no-secret 投影（信任内部用户）
- 复杂的 billing attribution（统一配额）
- 200+ 个安全相关测试

#### 要简化的
- `product_registry.py` → 简单的 users 表
- `api_keys.py` → 环境变量或简单 token
- 权限检查 → 仅区分 admin/user

#### 要保留的
- 用户基本信息和查询历史
- 简单的 admin/user 角色
- 基础的请求限流

**优势**: 代码量减少 40-50%，更容易维护  
**劣势**: 需要较大改动，测试需要重新调整

---

### 方案 C：混合方案（平衡）

**分两个 branch 进行**

1. **main 分支**: 保持当前状态，推送到 GitHub
2. **refocus/lightweight 分支**: 实施方案 B 的简化
3. 两周后评估，选择保留哪个

**优势**: 风险最低，可以并行尝试  
**劣势**: 需要维护两个分支
