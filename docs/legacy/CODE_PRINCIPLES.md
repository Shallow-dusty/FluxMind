# FluxMind 开发原则

**制定日期**: 2026-06-21  
**适用范围**: 所有后续开发工作  
**目的**: 防止过度工程，保持功能开发聚焦

---

## 🎯 项目定位

**FluxMind 是什么**：轻量级多用户研究辅助工具（5-20人）  
**FluxMind 不是什么**：企业级 SaaS 平台

### 用户场景
- **规模**: 5-20 人（实验室/课题组内部）
- **角色**: 导师（管理员）+ 学生（普通用户）
- **使用**: 内部使用，不对外公开
- **信任**: 用户之间互相信任，非对抗环境

---

## ⚠️ 防御性代码冻结原则

### 已完成的安全边界

FluxMind 已有足够的安全措施：
- ✅ 基础输入验证
- ✅ SQL 参数化查询
- ✅ 文件上传检查
- ✅ 基本权限控制
- ✅ 请求限流

### 停止以下工作

从 2026-06-21 起，**禁止**以下类型的开发：

#### ❌ 不再添加的防御措施
1. **No-secret 投影层**
   - 不再隐藏 request_id、owner_id、idempotency_key
   - 内部用户看到这些信息无安全风险
   - 调试时反而需要这些信息

2. **过度的错误清理**
   - 不再 sanitize Streamlit 错误输出
   - 不再 redact API 错误详情
   - 内部用户需要完整错误信息来调试

3. **复杂的审计追踪**
   - 不再为每个操作添加 metadata-only 事件
   - 不再添加复杂的 billing attribution
   - 简单的查询日志已足够

4. **企业级安全测试**
   - 不再为"潜在信息泄露"编写测试
   - 不再测试各种"不暴露 XX"场景
   - 聚焦功能测试而非安全测试

#### ✅ 仍然需要的防御措施
1. **基础安全**
   - SQL 注入防护（使用参数化查询）
   - 文件上传验证（PDF 格式、大小限制）
   - 权限检查（admin vs student）

2. **防误操作**
   - 危险操作需要确认
   - 删除操作需要 admin 权限
   - 基本的输入验证

3. **资源保护**
   - 请求频率限制
   - 上传文件大小限制
   - 查询超时控制

### 判断标准

**遇到"是否添加安全措施"时，问自己**：

1. **威胁模型**: 5-20 个互相信任的研究人员，这个"泄露"是威胁吗？
   - 如果答案是"不是" → 不添加

2. **实际价值**: 这个防御措施能防止什么实际问题？
   - 如果答案是"理论上可能" → 不添加
   - 如果答案是"确实会发生" → 添加

3. **开发成本**: 实现这个措施需要多少代码和测试？
   - 如果超过 100 行 → 重新评估必要性

## 🚀 功能开发优先级

### 核心原则

**价值优先**: 每个 PR 必须回答"这让用户更容易完成研究任务了吗？"

### 优先级排序（2026-06-21 确定）

1. **Priority 1: 扩充论文库** (30 → 50+ 篇)
   - 直接提升回答质量
   - 每周目标：添加 10 篇高质量论文

2. **Priority 2: 真实图像生成** (OpenAI DALL-E)
   - 替换 SVG mock
   - 能生成控制系统框图、波形图

3. **Priority 3: 真实代码执行** (Docker 沙箱)
   - 替换 subprocess mock
   - 安全执行用户的 Python/Octave 代码

4. **Priority 4: 多用户隔离**
   - 简单的用户管理（admin/student）
   - 每个人看到自己的查询历史

5. **Priority 5: 查询历史**
   - 可追溯过去的查询
   - 导师能看所有学生的查询

### 禁止的工作

在 Priority 1-3 完成之前，**不做**以下工作：
- ❌ 性能优化（除非严重影响使用）
- ❌ 代码重构（除非阻碍功能开发）
- ❌ 完美的测试覆盖（功能测试足够即可）
- ❌ 文档美化（简单清晰即可）

## 📏 代码复杂度控制

### 单个功能的代码量上限

| 组件 | 代码量上限 | 说明 |
|------|-----------|------|
| 单个功能实现 | 200 行 | 超过需要拆分 |
| 单个测试文件 | 300 行 | 超过需要分组 |
| 安全投影层 | 0 行 | 不再添加 |
| 文档更新 | 50 行 | 超过说明功能太复杂 |

### 比例原则

对于每个新功能：
```
功能代码 : 测试代码 : 文档 = 1 : 1.5 : 0.2
```

**错误示例**（最近 63 个提交）：
```
功能代码 : 测试代码 : 文档 = 1 : 4 : 5
```

## 🔄 Codex 工作流指导

### Codex /goal 使用原则

**设置目标时**：
1. 明确功能价值（对用户有什么用）
2. 设置时间限制（最多 1 周）
3. 定义完成标准（可演示的功能）

**禁止的目标设置**：
- ❌ "完善安全边界"（太模糊）
- ❌ "提升代码质量"（无终点）
- ❌ "增加测试覆盖率"（次要目标）
- ❌ "审计潜在问题"（会陷入循环）

**正确的目标设置**：
- ✅ "接入 OpenAI 图像生成，能生成 PMSM 控制框图"
- ✅ "添加 10 篇滑模控制论文到语料库"
- ✅ "实现简单的用户登录和历史查询"

### 自检清单

在每次开发前，Codex 应该问自己：

**功能价值检查**：
- [ ] 这个功能直接提升用户体验吗？
- [ ] 用户会主动使用这个功能吗？
- [ ] 这是 Priority 1-3 的任务吗？

**复杂度检查**：
- [ ] 功能实现 < 200 行？
- [ ] 测试代码 < 300 行？
- [ ] 文档更新 < 50 行？

**安全检查**（冻结原则）：
- [ ] 这是新的 no-secret 投影吗？→ 不做
- [ ] 这是新的错误清理吗？→ 不做
- [ ] 这是新的审计追踪吗？→ 不做

**如果任何一项不通过，重新评估任务的必要性**

## 🎓 学习 vs 过度工程

### 什么是好的严谨？

**✅ 值得投入的严谨**：
- 功能测试（确保功能正常工作）
- 架构设计（确保代码易于修改）
- 清晰文档（确保他人能理解）
- 用户体验（确保使用流畅）

**❌ 过度的严谨**：
- 100% 测试覆盖率（边际收益递减）
- 层层安全投影（内部用户不需要）
- 详尽的审计日志（简单日志足够）
- 完美的代码风格（一致即可）

### 时间分配原则

每周 40 小时开发时间：
- **30 小时**（75%）：新功能开发
- **6 小时**（15%）：测试和文档
- **4 小时**（10%）：重构和优化

**不是**：
- ~~10 小时功能 + 30 小时安全加固~~

## 📊 成功指标

### 短期（2 周）

- [ ] OpenAI 图像生成可用
- [ ] Docker 代码执行可用
- [ ] 论文库扩充到 50 篇
- [ ] 代码量增长 < 20%

### 中期（1 月）

- [ ] 5 个真实用户在使用
- [ ] 每天至少 10 次查询
- [ ] 用户反馈"很有用"
- [ ] 没有新的安全投影代码

### 长期（3 月）

- [ ] 成为实验室日常工具
- [ ] 论文库 100+ 篇
- [ ] 稳定运行无重大 bug
- [ ] 代码复杂度下降

---

## 🚨 红线

以下情况**立即停止并重新评估**：

1. **功能停滞超过 1 周**
   - 如果一周内没有新的用户可见功能 → 出问题了

2. **安全代码占比超过 20%**
   - 如果一次 PR 中，安全相关代码超过 20% → 走偏了

3. **测试代码是功能代码的 3 倍以上**
   - 正常比例应该是 1:1.5，超过 1:3 → 过度了

4. **连续 5 个提交都是"fix: sanitize XX"**
   - 说明陷入安全清理循环 → 立即停止
